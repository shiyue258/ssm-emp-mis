## 六、本轮发现的问题

E03 与 E04 两条用例**第一次执行时是失败的**，暴露了一个真实缺陷：

**现象**：`POST /health` 返回 HTTP 200 + `{"code":500,"message":"系统繁忙，请稍后重试"}`；`GET /emps/abc` 同样返回 200 + 系统繁忙。两者都应该是 4xx。

**根因**：`GlobalExceptionHandler` 中的兜底分支 `@ExceptionHandler(Exception.class)` 把 Spring 自己的 `HttpRequestMethodNotSupportedException` 与 `MethodArgumentTypeMismatchException` 一并捕获，翻译成了业务错误。异常处理器按「最具体优先」匹配，兜底分支排在最后，但如果**没有更具体的处理器存在**，它就会接管一切——包括那些本该由框架处理的协议级异常。

**为什么之前没发现**：第五次推送时实测过 `POST /health` 返回 405，那时 `GlobalExceptionHandler` 还没写；第六次加入兜底后行为被静默改变，而 README 里那句「分别返回 404、405」一直没有再复核。**兜底异常处理会改变框架默认的协议行为，这一条不在多数教程的提醒清单里。**

**修复**：为这两类异常各加一个具体处理器，并用 `@ResponseStatus` 指定正确状态码，同时让 body 的 `code` 与 HTTP 状态一致（405 / 400）。修复后 E03、E04 均通过。

这条留在这里而不是抹掉，是因为它演示了用例集的实际作用：**它测的不是「代码能不能跑」，而是「改了 A 之后 B 有没有坏」。**
